# Heurēka! microgame map: computer science

Compiled 2026-11-05. This file maps computer science, from a young child's first program through intro university courses and current AI, to proposed Heurēka! microgames. It points to the Q.E.D.! math map (docs/CURRICULUM.md) instead of repeating its games.

## How to read this file

- **A microgame is a 3 to 6 second moment, not a question.** One shouted verb names a goal; the player reaches it with one kind of action (drag, swipe, tap, hold); and something happens on screen that makes an idea visible. The player learns by doing it, seeing it happen, failing in a funny way, doing it again faster, and reading the card afterwards. No game asks a question, asks the player to predict, or asks for a calculated number.
- **What gets the most games.** Software today is often built with AI help, so the file gives the most games to what matters when you build that way: how an app fits together, how the web works at the level a builder needs, data modelling, reading code and spotting what it does wrong, testing with weird inputs, debugging by narrowing down, version control as a safety net, deploying, the security and privacy mistakes builders actually make, cost and speed, and working with AI tools. The core of how programs run keeps a full part, because you have to be able to read what an AI wrote. Low-level topics (CPU and memory internals, number formats, sorting algorithm details, formal big-O, automata and computability) shrink to a few games in Part 15 or to pointers into the math map.
- **Units, sources and "Why it matters".** Each unit has a **Sources** line naming the real course units it covers, and a **Why it matters** line saying where the idea is used in real work. Course codes: CSF = Code.org CS Fundamentals (elementary); CSD = Code.org CS Discoveries (middle school); CSP = AP Computer Science Principles (College Board CED topic numbers); CSA = AP Computer Science A (2025-26 CED); CS50 = Harvard CS50 (Fall 2025 weeks); CS50 Cyber = CS50's Introduction to Cybersecurity; 6.006 = MIT Introduction to Algorithms (Spring 2020 lectures); 6.1200 = MIT Mathematics for Computer Science (formerly 6.042J); 15-213 = CMU Introduction to Computer Systems; CS144 = Stanford Introduction to Computer Networking (Fall 2026); 15-445 = CMU Database Systems (Fall 2025); MS = MIT "The Missing Semester of Your CS Education" (2026); 6.5840 = MIT Distributed Systems (Spring 2026); MLCC = Google Machine Learning Crash Course; CS336 = Stanford Language Modeling from Scratch (Spring 2026); 18.404 = MIT Theory of Computation (Fall 2020); OWASP LLM = OWASP Top 10 for LLM Applications 2025. Full citations are under "Sources" at the end. Where a unit's topic is not in any of these courses (for example feature flags or pagination), its Sources line says so.
- **Columns** (one row per microgame):
  - **ID**: a stable reference; the letters name the part (EL, PR, AP, WB, DM, RD, VC, SC, PV, SP, BA, AI, ST, IV, DS, UH).
  - **Command**: a verb the player does, one or two words, in capitals, ending in "!".
  - **Concept**: the one plain sentence the player comes to see; it is also the first line of the card shown after the game.
  - **Scene**: what is on screen in the first second.
  - **Action**: the one thing the player does.
  - **What happens**: the success, with the idea made visible.
  - **Funny fail**: the common mistake, what happens, and how that also shows the idea.
  - **Level 2**: the same action made harder, or one twist.
  - **Host**: the animal that acts it out (frog, ant, penguin, duck, turtle, octopus, owl, fox, rabbit, beaver, hedgehog, bird, plus extras such as a robot, squirrels or fireflies where a scene needs them).
- **"See X"** rows point to a game already in the Q.E.D.! math map (IDs such as X-30) or elsewhere in this file. Their ID cell is "—", and they are not counted.
- **[WEAK FIT]** marks the 2 ideas that are hard to turn into a 3 to 6 second action; each still gets its best playable version.
- **The clarity bar.** A young child who has never seen the topic should see what to do in the first second and be able to follow what happens, even in the university-level games. The idea can be advanced; the picture and the action must be plain.

## The signature mechanic: you are the computer

Wherever a program runs in this file (loops, conditions, functions, recursion, data structures, debugging, and reading code an AI wrote), the game uses one look, so a player learns the visual language once.

- **The code panel** sits on the left: a tiny real Python program, 2 to 6 lines (Java, JavaScript or SQL only where the unit is about that language). The current line glows. At level 0 each line has a small picture beside it (an arrow for `forward()`, a gem for `pick_gem()`, a looping arrow for `for`), so a newcomer can follow it without knowing Python.
- **The world** sits on the right: a maze, a kitchen, a dock, a shop. A robot, an animal or a pair of hands does what the code says, and the player is the one who makes it happen: the player drags the robot one step, turns it, picks up the gem, or puts a value in a box, exactly as the glowing line says.
- **The program's state is drawn as objects in the world:** each variable is a labelled box on a shelf; a list is a row of cups; the loop counter is a tally counter on the wall that the player clicks; the call stack is a pile of plates, one per function call, each plate with a sticky note saying which line to come back to; printed output is a speech bubble.
- **Doing what the line says** moves the glow to the next line. **Doing something else** makes the world go wrong in a funny way (the robot walks into the pond, the cup overflows), and the line that was misread flashes. The game rewinds to that line and the player tries again.
- **In fix-it games** the program itself is wrong. The player acts it out faithfully, watches the world go wrong, then drags one line or one piece of a line into the right shape and acts it out again.

The other shared pictures: a hash map is a wall of labelled lockers; a tree is a family tree you climb; a graph is a subway map; a queue is a line at a shop; git history is a railway with sidings; a network message is an envelope carried between towns; a cache is a backpack of things you use often; a key is a padlock; speed is a pile of pebbles, one per step, with the slow and fast piles side by side.

## What was cut or shrunk, and why

- **Questions and calculations.** No game asks the player to answer, predict or compute. Ideas that courses teach mainly through calculation (big-O formulas, subnet arithmetic, RSA with small numbers, cache hit rates, page-table arithmetic, speed-up formulas) appear as pictures of the idea, or point to the math map.
- **Low-level topics**, following the owner's steer that low-level details matter less when building with AI: CPU and memory internals, number representation, operating systems, sorting algorithm details, formal big-O and theory of computation are cut to a few games each in Part 15. Assembly (15-213 L3 to L6) and linking (L7) are left out.
- **Java-only details from AP CSA**: wrapper classes (CSA 4.7) and casting rules (1.5) are left out. Inheritance is not in the 2025-26 CSA CED; SPEAK! (ST-23) keeps polymorphism because real code uses it.
- **Algorithm details used mainly in exams**: AVL rotation cases (6.006 L7) shrink to ROTATE! (ST-08); all-pairs shortest paths and Johnson's algorithm (L14) and Bellman-Ford (L12) are left out; Dijkstra is the math map's X-20. Quicksort, merge sort and insertion sort shrink to one act-it-out sorting game (SWAP CARDS!, ST-11) and one game on why sort order and stability matter (KEEP ORDER!, ST-12).
- **Theory of computation (18.404)**: pumping lemmas, context-free grammars, PSPACE, space complexity, hierarchy theorems and interactive proofs are left out. Regular expressions (used daily), finite-state machines, the halting problem and the idea behind P vs NP stay, in Part 15.
- **Database internals (15-445)**: storage layout, buffer pools, join algorithms, query optimizers, timestamp ordering and MVCC are left out. Keys, joins, indexes, transactions, locking, migrations and backups stay. SQL's rules for missing values (NULL) were cut, because they would need a question rather than an action.
- **The CSP exam pseudocode language** is not used.

## Part 0: Elementary

Sources: CSF Express course (2020-21 lesson list): "Programming with Angry Birds" (sequencing), "Debugging with Scrat", "Loops with Rey and BB-8", "Nested Loops in Maze", "If/Else with Bee", "While Loops with the Farmer", "Until Loops in Maze", "Functions with Harvester", "Variables with Artist", "Behaviors in Sprite Lab" (events); CSP 5.6 "Safe Computing" for the online-safety games.
Why it matters: putting steps in order, repeating them, choosing between them and fixing them when they go wrong are the habits under every later part of this file.

Every game here uses pictures and actions only. Programs are strips of picture cards (arrows, a curled ribbon for "repeat", a card with a flower or a carrot on it). There are no symbols, and the only words on screen are short ones a young child reads easily ("go"). The first two games introduce the signature mechanic in its simplest form: the child is the computer, moving the character card by card.

## Part 1: How programs run (you are the computer)

| RD-08 | `NARROW!` | To find a bug, switch off half the program and see if it still breaks. | A 16-step recipe-robot that burns the cake somewhere; light switches beside each half. | Switch off half the steps and bake again; keep halving the half that still burns. | Four bakes later, one step is left glowing: "oven at 500". | Checking steps one by one from the top: the bell rings while the hedgehog is still on step nine. | Two bugs at once | Hedgehog (baker) |
| RD-09 | `BIN IT!` | Errors come in kinds: the program won't start, it crashes, or it gives a wrong answer. | Three broken programs on a conveyor; bins with pictures: a locked door, a puff of smoke, a lopsided cake. | Flick each program into its bin as it passes. | Each plays out in its bin: the door won't open, a puff of smoke, a cake twice as big as the recipe. | Binning the lopsided cake as "won't start": it starts happily and the wrong cake rolls out. | Add "runs forever" | Frog |

| ID | Command | Concept | Scene | Action | What happens | Funny fail | Level 2 | Host |
|---|---|---|---|---|---|---|---|---|
| RD-10 | `BREAK IT!` | Good tests feed in the weird inputs (empty, huge, emoji), because that is where bugs hide. | A sign-up form machine that passed two easy tests; a pile of inputs: an empty name, a name a mile long, a name made of emoji, a normal name. | Throw inputs into the machine until it breaks. | The empty name makes it cough smoke, the long one jams it, the emoji come out garbled: three bugs found, each stamped on a bug card. | Throwing only normal names: green lights all round, until real users arrive with emoji and the machine explodes in confetti of garbled letters. | Negative ages, dates from the future | Beaver |
| RD-11 | `TEST IT!` | One well-chosen test can catch a bug that many easy tests miss. | A leap-year checker that only checks "divides by 4"; calendar pages drift past: 2024, 2023, 1900, 2000. | Grab the page that makes the checker go wrong and drop it in. | 1900 comes out with a false 29 February that flutters off the page in red. | Dropping in 2024: green light, the bug still hiding. | Cover every rule with the fewest pages | Rabbit |
| RD-12 | `GUARD!` | Programs should reject bad input at the door, before it gets inside. | A pet-age box at a vet's door; inputs arrive: 3, −5, "banana", 900. | Fit the guard gate ("a number from 0 to 40") on the door. | Good ages walk in; the others bounce off politely. | No guard: "banana" gets in, and later a dog is booked for a banana-year check-up. | Friendly messages for each kind of bad input | Owl |

## Part 6: Version control, deploying and environments

Sources: MS 2026 "Version Control and Git", "Packaging and Shipping Code", "Command-line Environment", "Introduction to the Shell", "Development Environment and Tools", "Beyond the Code"; CSP 1.1 "Collaboration", 1.3 "Program Design and Development"; CS50 Week 9 "Flask". Feature flags and staging environments are standard practice, not course units.
Why it matters: version control is the safety net that lets you try things (and let an AI try things) without fear, and deploying is where working code meets real users. Git history is drawn as a railway: each commit is a carriage, a branch is a siding, and a merge joins two tracks.

### 6.1 Version control as a safety net
| ID | Command | Concept | Scene | Action | What happens | Funny fail | Level 2 | Host |
|---|---|---|---|---|---|---|---|---|
| VC-01 | `COUPLE!` | A commit saves a snapshot of the changes you chose as a new carriage on the train. | A train of carriages on the main line; two changed files on the platform; a loading bay. | Drag the file you mean to save into the loading bay, then couple the new carriage to the train. | The new carriage clicks on with the file inside; the other changed file stays on the platform, unsaved. | Coupling an empty carriage: it rolls on with nothing inside, and the conductor taps its empty seats. | Uncouple back to an older carriage | Beaver (conductor) |
| VC-02 | `BRANCH OFF!` | A branch lets you try something on a siding without touching the main line. | The main line with a working train; a half-built feature that might break things. | Throw the points to a siding and build the new carriages there. | Main-line trains keep running on time while the siding grows. | Building on the main line: the half-built carriage derails the main train, and passengers climb out grumbling. | Two sidings at once | Squirrel |
| VC-03 | `RESOLVE!` | When two branches change the same line, a person decides what that line should be (a merge conflict). | Two trains from two sidings arrive at one track at the same time, each carrying a different version of the same line. | Let one train through, or move carriages so the track carries the right combination, then clear the signal. | The merged train rolls onto the main line and the program runs. | Leaving both trains on the track: they lock bumpers in the middle (the conflict markers stay in the file), and nothing moves. | Both changes are needed: combine them | Fox, rabbit (two drivers) |
| VC-04 | `REVERT!` | Reverting adds a new carriage that undoes a bad one, so the history stays honest. | A carriage that broke the site sits in the middle of the train. | Couple a mirror carriage to the end that cancels out the bad one. | The site works again, and the history still shows both what went wrong and the fix. | Ripping the bad carriage out of the middle: everyone else's copies of the train no longer match, and the station board flickers with errors. | Revert a merge | Beaver |
| VC-05 | `BISECT!` | Halving the history finds the commit that broke something in a few tests. | A long train; a bug appeared somewhere along it. | Test the middle carriage, then the middle of the half that's left, until one carriage remains. | Each test greys out half the train, and the guilty carriage lights up. | Testing carriages one by one from the engine: the owl is still testing when the bell rings. | A test that lies sometimes | Owl |
| VC-06 | `FREEZE!` | Pinning exact versions of your dependencies stops surprise updates from breaking your app. | An app built from library blocks; one library silently updates overnight and changes shape. | Clip a version tag (a lockfile) onto every library block before night falls. | Overnight the library updates in the shop, but your app keeps the exact blocks it was tested with. | Not pinning: the new block doesn't fit, and the app crumbles in the morning. | Update on purpose, test, then pin again | Beaver |

### 6.2 Shipping and running
| ID | Command | Concept | Scene | Action | What happens | Funny fail | Level 2 | Host |
|---|---|---|---|---|---|---|---|---|
| VC-07 | `SHIP!` | A deployment pipeline runs the tests before release, so broken code never reaches users. | A conveyor with stations: install, test, build, release; one test is broken. | Arrange the stations with test before release, and start the conveyor. | The broken test stops the conveyor, and users never see the bug. | Release before test: the broken site ships, and users' screens go blank. | Roll back with one lever | Beaver |
| VC-08 | `PROMOTE!` | Code goes through environments: your computer, a staging copy, then production. | Three stages: a workbench, a rehearsal stage with fake customers, and the real shop. | Move the new feature to rehearsal first, watch it, then promote it to the real shop. | The rehearsal catches a squeaky door; it's oiled before real customers arrive. | Going straight from the workbench to the real shop: the door falls off in front of the customers. | A rehearsal that uses a copy of real data safely | Owl |
| VC-09 | `CONFIGURE!` | The same code reads different settings in each environment, so testing never touches real data. | The app's settings box; two databases, a sandbox one and the real one. | Plug the workbench's settings into the sandbox database. | Tests create and delete pretend users in the sandbox; real users are untouched. | Plugging the workbench into the real database: a test run deletes every real user, and the beaver gasps. | Different keys per environment (see HIDE KEY!, SC-01) | Beaver |
| VC-10 | `FLIP!` | A feature flag turns a new feature on for a few users first, and off at once if it misbehaves. | A new button behind a switch on the wall; a crowd of users. | Flip it on for a small group, watch the error lamp, and flip it off when it blinks. | Only a few users see the bug, and one flip hides it from everyone. | Turning it on for everyone: the whole crowd hits the bug at once. | Raise the share slowly | Fox |
| VC-11 | `BUMP!` | Version numbers say how big a change is: fix, new feature, or breaking change. | A library at version 2.4.1; a bug fix, a new feature and a change that breaks old code arrive. | Bump the right digit for each change. | Programs that asked for "version 2" keep working with the fix and the feature, and refuse the breaking one safely. | Bumping only the middle digit for the breaking change: a program that trusted version 2 updates and crashes. | Two libraries needing different versions | Owl |
| VC-12 | `DIG IN!` | Logs and graphs show what happened and when. | A site slowed down at lunchtime; logs stream past; an error graph spikes; the timeline has a "deploy" marker. | Filter the logs to errors, then drag the deploy marker next to the spike. | The errors all come from one new function, and the spike starts right after the deploy. | Blaming the lunch rush: yesterday's graph slides in, just as busy, with no spike. | An alert for the next spike | Owl |
| VC-13 | `NAVIGATE!` | Folders nest like rooms; ".." means the room that contains this one. | A house of nested rooms; the frog is in "docs" and must reach "photos" next door. | Drag the frog through the ".." door, then into photos. | The frog climbs up to the room that holds both, walks into photos, and the path writes itself as a label. | Treating ".." as "back where I was": the frog ends up in the wrong wing. | Absolute paths from the front door | Frog |
| VC-14 | `PIPE!` | Small command-line tools connected by pipes do big jobs. | A huge log file; tools: "read", "keep ERROR lines", "count". | Connect the three tools with pipe pieces in order. | Lines flow through; only ERROR lines pass the filter, and the counter clicks for each. The command `cat log.txt \| grep ERROR \| wc -l` writes itself as a label. | Putting "count" before the filter: it counts every line, and the beaver drowns in a flood of lines. | Count each kind of error | Beaver |

## Part 7: Security mistakes builders make

Sources: CS50 Cyber Lecture 0 "Securing Accounts", Lecture 1 "Securing Data", Lecture 2 "Securing Systems", Lecture 3 "Securing Software"; CS50 Week 7 (SQL injection), Week 8; CSP 5.6 "Safe Computing"; 6.1200 "Elementary number theory and cryptography". The arithmetic behind RSA is in the math map: X-04 MODULO!, X-05 MOD INVERSE!, X-09 EUCLID!.
Why it matters: the breaches that hit small apps usually come from a few repeated mistakes: leaked keys, injection, missing permission checks, trusting what the user sends, and storing passwords badly. AI-written code makes these mistakes too, so a builder has to spot them.

### 7.1 Mistakes in the code
| ID | Command | Concept | Scene | Action | What happens | Funny fail | Level 2 | Host |
|---|---|---|---|---|---|---|---|---|
| SC-01 | `HIDE KEY!` | Secrets like API keys must stay out of the code you share. | A project about to be pushed to a public site; a secret key is written in one file; a fox-bot prowls the site. | Drag the key into a locked environment box and put its file on the ignore list before pushing. | The public copy shows only "read the key from the box", and the fox-bot finds nothing. | Pushing as it is: the fox-bot finds the key within moments and starts spending your money. | A key already pushed must be replaced | Fox |
| SC-02 | `BIND!` | Typed text must travel as data, never glued into code (SQL injection). | Code panel: a login query built by gluing in the typed name; a fox types a name full of quotes. | Swap the glued-in name for a sealed envelope (a placeholder), then act the query out. | The envelope arrives sealed, the database never reads it as code, and the trick name simply doesn't match. | Gluing it in: the quotes close the query early, the password check vanishes, and the vault door swings open. | A search box with the same hole | Fox |
| SC-03 | `ESCAPE!` | Text shown on a page must be escaped so it can't run as code (cross-site scripting). | A comment wall; a fox posts a comment that is secretly a script. | Run the escaping brush over the wall. | The script's brackets turn into plain printed symbols, and the comment sits there harmlessly. | Not escaping: the script runs in every reader's browser, and their login tickets fly to the fox. | A script hidden in a link | Fox |
| SC-04 | `CHECK BADGE!` | Being logged in is not enough: the server must check that this thing is yours. | Order pages numbered in the address bar; you are logged in and looking at order 41. | Fit the "is this order yours?" check on the server's door, then try order 42. | Order 42 stays locked; only your own orders open. | No check: changing 41 to 42 in the address opens a stranger's order, address and all, and the fox scribbles it down. | Admin-only pages | Owl (badge checker) |
| SC-05 | `VALIDATE!` | Never trust what the user's screen sends; check it again on the server. | A shop's checkout parcel arrives at the server carrying the price; a fox has edited its parcel. | Fit the "look up the real price" step on the server before charging. | The server ignores the parcel's price and charges the real one. | Trusting the parcel: the fox buys a bike for one penny and rides off grinning. | Quantities of minus three | Fox |
| SC-06 | `HASH!` | Store a fingerprint (hash) of each password, not the password itself. | A login desk and a filing cabinet; a hash mill that turns any password into a scrambled fingerprint. | Feed each password through the mill before filing it. | The cabinet holds only fingerprints; when the fox steals it, it finds scrambles and must guess one by one. | Filing passwords as they are: the fox opens the drawer and reads every password at once. | Slow-on-purpose hashes | Owl |
| SC-07 | `SALT!` | A random salt makes identical passwords get different fingerprints. | Two users with the same password have identical fingerprints, and the fox's book of ready-made fingerprints matches both. | Sprinkle a different salt on each password before the mill. | The fingerprints come out different, and the ready-made book matches nothing. | Using the same salt for both: the fingerprints still match, and the fox ticks them off together. | A secret pepper kept elsewhere | Owl |
| SC-08 | `THROTTLE!` | Limiting attempts stops bots from guessing passwords at high speed. | A login door; a fox-bot fires guesses like a machine gun. | Fit a turnstile that lets in only a few tries per minute. | The bot's guesses pile up at the turnstile, and real users still get through. | No limit: the bot guesses through a whole dictionary before lunch and the door opens. | Lock after many fails, but not for the real owner | Fox |
| SC-09 | `UPDATE!` | Old library versions with known holes are an easy way in; keep dependencies updated. | An app built from library blocks; one block has a known crack marked on the public noticeboard. | Swap the cracked block for its patched version. | The crack seals, and the fox reading the noticeboard finds nothing to use. | Leaving it: the fox reads the noticeboard, walks straight to the crack, and climbs in. | Update without breaking anything (see FREEZE!, VC-06) | Fox |

### 7.2 Mistakes people make
| ID | Command | Concept | Scene | Action | What happens | Funny fail | Level 2 | Host |
|---|---|---|---|---|---|---|---|---|
| SC-10 | `LENGTHEN!` | Every extra random word multiplies the guesses an attacker needs. | A fox speed-reading a guessing book toward your password. | Tap to add random words to your password while the fox reads. | The book thickens many times over with each word, until the fox can't lift it. | Adding "123" on the end: the fox flips to a chapter called "common tricks" and finds it. | One password reused everywhere | Fox |
| SC-11 | `HANG UP!` | A second factor stops a thief who has your password, unless you hand it over. | A fox at the door with your stolen password; your phone shows a code that changes every few seconds; the phone rings: "It's the bank, read me your code." | Hang up the call. | The fox stands at the door without the code, and the code on the phone keeps changing. | Reading the code out: the door opens for the fox, and the owl at the bank facepalms. | A passkey that a fake website can't use | Fox, owl |
| SC-12 | `SPOT!` | The real owner of a web address is the name just before the first single slash. | Email links scroll past; some say "bank.example" somewhere but belong to someone else. | Tap the owner part of each link to reveal who really owns it. | Real links open the bank; fake ones peel off their disguise and show a fox. | Trusting a link that starts with "bank.example" but ends in another owner's name: the fox's mask slips off. | A look-alike letter in the name | Fox |

## Part 8: Privacy, accessibility and fairness

Sources: CSP 5.1 "Beneficial and Harmful Effects", 5.2 "Digital Divide", 5.3 "Computing Bias", 5.4 "Crowdsourcing", 5.5 "Legal and Ethical Concerns", 5.6 "Safe Computing"; CSA 4.1 "Ethical and Social Issues Around Data Collection"; CS50 Cyber Lecture 4 "Preserving Privacy"; CSD Unit 4 "The Design Process", Unit 5 "Data and Society". Bias in AI models is AI-39 REBALANCE!.
Why it matters: an app collects, keeps and shows data about real people, and real people with different abilities and connections use it; privacy, access and fairness problems are design decisions a builder makes, often without noticing.

| ID | Command | Concept | Scene | Action | What happens | Funny fail | Level 2 | Host |
|---|---|---|---|---|---|---|---|---|
| PV-01 | `TRIM!` | Collect only the data you need; data you never collected can't leak. | A sign-up form asking for name, email, home address, birthday, mother's maiden name; a storm cloud labelled "breach" on the horizon. | Swipe away every field the app doesn't need. | The breach hits, and the fox finds only names and emails in the drawer. | Keeping everything: the fox walks off with a sack of addresses and birthdays. | A field you need for a while, then delete | Owl |
| PV-02 | `ASK FIRST!` | Consent means the person chooses, with nothing ticked for them. | A cookie banner whose boxes are already ticked; a rabbit about to click "OK". | Untick the boxes so the rabbit starts with nothing shared, and make "No thanks" as big as "OK". | The rabbit picks what it is happy with, and only that is shared. | Leaving the boxes ticked: the rabbit's every click is followed by a parade of tiny trackers. | A dark pattern: the "cancel" link is hidden | Rabbit |
| PV-03 | `ERASE!` | Deleting someone's data means deleting it everywhere it was copied. | A user asks to be deleted; their data sits in the database, the backups, the logs and an analytics tool. | Sweep the user out of every place their data lives. | Every copy fades, and the user's ghost waves goodbye. | Deleting only the database row: the user's face keeps popping up from the analytics tool. | Backups that expire on their own | Hedgehog (sweeper) |

## Part 9: Speed and cost

Sources: CSP 3.17 "Algorithmic Efficiency" (title reconstructed); CSA 2.12 "Informal Run-Time Analysis"; CS50 Week 3; 6.006 L1 "Introduction"; 15-213 "The Memory Hierarchy", "Cache Memories", "Code Optimization"; MS 2026 "Debugging and Profiling"; 6.5840 "Cache Consistency: Memcached at Facebook". Pagination, lazy loading and cloud billing are standard practice, not course units.
Why it matters: when an app is slow or expensive, the cause is usually too many calls, missing caches, loading too much at once, or work that grows too fast with the data; each one is easy to see once you know the picture.

| ID | Command | Concept | Scene | Action | What happens | Funny fail | Level 2 | Host |
|---|---|---|---|---|---|---|---|---|
| SP-01 | `BATCH!` | One request for fifty things is far faster than fifty separate requests. | A screen needs fifty friends' pictures; a bird flies to the server and back for each one. | Gather the fifty requests into one sack and send the bird once. | One round trip brings everything, and the screen fills at once. | Sending them one by one: the bird is still flapping back and forth when the user gives up. | Batch, but not so big the sack bursts | Bird |
| SP-02 | `PREFETCH!` | Loading a list and then making one more query for each item (the N+1 problem) is slow; fetch them together. | Code panel: load 20 posts, then for each post load its author. Acted out, the robot runs to the database 21 times. | Swap the loop's query for a single join that brings posts and authors together. | One trip brings back posts with their authors attached. | Leaving the loop: the robot's trips stack up as a tower of pebbles while the page spins. | Comments under each post | Robot |
| SP-03 | `STASH!` | A cache keeps things you use often close at hand. | A hiker keeps walking back to a far-off hut for the same water bottle; a backpack hangs empty. | Put the most-used items in the backpack. | The hiker grabs them on the move, and trips to the hut almost stop. | Stuffing everything in the backpack: it's too heavy to lift, and the hiker topples over. | A small backpack: choose what stays | Turtle (hiker) |

## Part 13: Coding interview patterns (a pilot for a possible separate app)

Sources: the classic practice problems on LeetCode and similar sites. Each problem is described here in our own words with our own example. Related course units: 6.006 L2–L10, CSA 4.14–4.17, CS50 Weeks 3 and 5.
Why it matters: technical interviews at software companies use problems like these, and the same patterns (hash maps, two pointers, sliding windows, stacks, flood fill, tables of remembered answers) solve everyday problems in real code.

### Shared format for every game in this unit

The owner may grow this unit into its own app, so all 12 games share one format, built on the signature mechanic. They can run a little longer than other games (up to about 10 seconds), but each step is one quick tap or drag.
- **The code panel** shows the pattern's few key lines; the current line glows, and the player acts it out.
- **A small input on the dock**: cups or tiles with positions painted above them, or a small grid.
- **Pointers are animals standing on cups**: the frog on the left and the rabbit on the right; other helpers are named by their job.
- **The helper structure sits right under the dock and always looks the same**: a hash map is a wall of lockers; a stack is a pile of plates; a queue is a short line; a heap is a pyramid of nests; a linked list is rafts tied by ropes.
- **Same controls everywhere**: tap the host to take the next step, or drag a pointer or item to where it goes next; both work. Routine steps run by themselves, and the player makes the 2 to 5 moves where the pattern decides something.
- **Slow way first**: each game opens with a quick ghost run of the brute-force method on the same input, dropping pebbles as it goes. The player's pattern then runs with its own pile, and both piles stay side by side. A last picture scales both up to a much bigger input, where the slow pile no longer fits on the screen.
- **Level 2** is the same problem with a twist (repeats, an empty input, a bigger input) and no glow on the next move.

### How the pilot would scale into its own app

- **Patterns to add**: monotonic stack (the next taller animal in a line), backtracking (every way to seat three animals; queens on a small board), union-find (which friend groups are joined), tries (word prefixes and autocomplete), meeting rooms with a heap, BFS on grids with walls, Dijkstra on weighted maps, bit tricks (the one unpaired sock found with XOR), prefix sums (a running total that answers "how much between here and there"), fast and slow pointers (a loop in a chain of rafts), binary search on the answer (the smallest boat that ships everything in time), greedy choices (jump game, gas stations), 2D tables of remembered answers (edit distance, grid paths, longest common subsequence), and tree walks (level by level, lowest common ancestor, checking a search tree).
- **Difficulty inside each pattern**: level 0 is a small input with the deciding moves glowing; level 1 is a bigger input with a twist (repeats, negative values, an empty input); level 2 combines two patterns (a sliding window that counts with a hash map; BFS with a visited set on a grid with walls) and drops the glow. After a pattern's three levels, a "spot the pattern" round shows a new problem as a scene, and the player picks up the tool that fits (lockers, plates, two animals, a window) and solves it with that tool.
- **Order across the app**: arrays and hash maps, then two pointers and windows, stacks and queues, linked lists, trees, graphs, heaps, tables of remembered answers, and backtracking last, so each pattern builds on the ones before it.
- **Keep the shared format**: the same code panel, dock, animals as pointers, lockers and plates, and the slow-way-first opener, so a player who learns the picture of a hash map in PAIR UP! recognises it in every later game.

## Part 14: Systems at scale

Sources: 6.5840 "Introduction", "GFS", "Fault Tolerance: Raft", "Consistency and Linearizability", "Distributed Transactions"; CSP 4.2 "Fault Tolerance", 4.3 "Parallel and Distributed Computing"; 15-445 "#23 Distributed Database Systems I".
Why it matters: once an app has many users it runs on many machines, and copies, failures, retries and splitting data decide whether it stays up and stays correct. Managed cloud services handle much of this, so a builder mainly needs the ideas.

| ID | Command | Concept | Scene | Action | What happens | Funny fail | Level 2 | Host |
|---|---|---|---|---|---|---|---|---|
| DS-01 | `FAIL OVER!` | Keeping copies on other machines lets another one take over when one fails. | A main server with two backups; the main server catches fire. | Tap the up-to-date backup to promote it. | The backup takes over, and customers keep shopping without noticing. | Promoting a backup that missed the last update: the newest order vanishes, and a beaver stares at its empty basket. | Backups that lag a few seconds | Beavers |
| DS-02 | `DEDUPE!` | Retries are safe only if the server can tell a repeat from a new request. | A payment flies to the bank, times out, and the app sends it again. | Clip an order-number tag onto the payment before sending. | The bank sees the same tag twice and ignores the repeat; the customer pays once. | No tag: the customer is charged twice, and the squirrel banker apologises. | A queue that delivers some messages twice | Squirrel |
| DS-03 | `BACK OFF!` | When many clients retry, waiting longer each time, with a bit of randomness, lets the server recover. | A server restarts; a flock of phones waits to retry. | Spread the flock's retries out by stretching the wait between tries. | The retries arrive spread out, and the server stands up and serves them all. | Everyone retrying at once: the server is knocked flat again, feathers everywhere. | A longest-wait limit | Birds |

| DS-06 | `VOTE!` | A leader needs a majority of votes, so a split network can't elect two leaders. | Five owls on a branch; the branch snaps into a group of two and a group of three. | Get a candidate elected in each group by tapping owls to vote. | The group of three reaches a majority and elects a leader; the group of two can't, and waits. | Trying to crown a leader with two votes: the crown won't fit, because two is not a majority of five. | The branch heals; the old leader steps down | Owls |

Selling: both sell, and when contact returns one customer gets an apology and a refund. | Wanting both at once: the reconnection shows two receipts for one item, and both penguins blush. | A bank balance versus a like counter | Penguins |

## Part 15: Under the hood

Sources: CSP 2.1 "Binary Numbers", 2.2 "Data Compression", 3.18 "Undecidable Problems"; CS50 Weeks 0, 4 and 5; 15-213 "Bits, Bytes, & Integers", "Machine Programming (Part I)", "Dynamic Memory Allocation: Basic", "Processes and Multitasking", "Synchronization: Basic", "Synchronization: Advanced", "Thread-Level Parallelism"; 6.1200 "State machines and invariants", "Induction and proof by contradiction"; 18.404 "Introduction, Finite Automata, Regular Expressions", "Undecidability", "P and NP, SAT, Poly-time Reducibility". Why it matters: these ideas explain the odd bugs that still reach builders (money that doesn't add up, emoji that break, counters that wrap, two requests that clash) and what a computer can and cannot do. They get fewer games because AI tools and managed services hide most of the details.

## The 10 games to build first

Chosen for being fun to play, teaching an idea builders use constantly, and setting up a shared picture that later games reuse.

1. **LOOP! (PR-02)**: the reference game for the signature mechanic (code panel, glowing line, tally counter on the wall, robot in a maze).
2. **TAG ALONG! (PR-15)**: two name tags on one row of cups; it makes aliasing, a confusing bug, obvious in one move.
3. **CALL! (PR-19)**: the plate pile as the call stack; the third reference game for the signature mechanic.
4. **WIRE UP! (AP-01)**: screen, server and database wired together; the fox reading the diary makes the point at once.
5. **BREAK IT! (RD-10)**: throwing empty, huge and emoji inputs at a machine is pure fun, and it is the habit that catches real bugs.
6. **RESOLVE! (VC-03)**: two trains on one track turns the dreaded merge conflict into a toy.
7. **HIDE KEY! (SC-01)**: the fox-bot finding a pushed API key is vivid and teaches the most common real leak.
8. **CHECK BADGE! (SC-04)**: changing an order number in the address bar and seeing a stranger's order teaches missing authorization in seconds.
9. **IGNORE! (BA-15)**: prompt injection acted out with an email agent; the most important new security idea for AI builders.
10. **NEXT! (AI-02)**: pulling the next word down from a bar chart shows what a language model is actually doing.

## Self-review

The file went through several owner steers while it was being written: concepts instead of calculations, the verb-and-goal format with no questions or predictions, "you are the computer" as the signature mechanic, and a reweighting toward building software with AI help. Every row in the final file was written after those steers, so earlier drafts' calculation and question rows are gone rather than patched. Specific choices made in review:
- Rows that were questions in earlier drafts became goals: "which is faster?" became RACE! (feed the mountain to a machine and switch if it chokes); "will it crash?" became SKIP! (don't reach into the closed box); "who wins at size n?" became the pebble piles in RACE! and UNTANGLE!.
- Calculation rows were cut or turned into pictures: RSA with small numbers became SNAP SHUT! and a pointer to the math map; image file size became STRETCH! and then was cut in the reweighting; subnet masks, page-table arithmetic and cache hit rates were dropped.
- Low-level parts (number formats, CPU, operating systems, concurrency, sorting algorithms, automata and computability) were moved into Part 15 and cut to 18 games.
- The two [WEAK FIT] rows (WEIGH UP!, PV-12, and OUTWIT!, UH-16) were kept because the ideas are important, with their best playable version.
- Known limits: the robot used as a host in Part 1 is not in the current animal cast (ANI) and needs drawing; some hosts are cast extras (squirrels, fireflies, ants as workers). A few course unit titles are reconstructed rather than fetched (see Sources).
